# ReFit and EDA: methodological distinction, transfer burden, and paper positioning

**2026-10-12 — codex-1.** Requested by the owner for the authors integrating `paper/claude_final`. This is an analysis and proposed wording document; no paper files were edited. No EDA training or comparative performance experiment was run. Source inspection uses EDA paper **arXiv:2603.09527v1** and release commit **`a29f0381479a92d0f3114fd264cd790bab3a208b`**. Technical findings below distinguish the paper, the released implementation, and our engineering deductions.

## 1. The distinction worth making

**ReFit's strongest distinction from EDA is repair within the architecture and serving contract of an existing released drafter.** ReFit-interface changes only the existing target-feature fusion projection. ReFit-full retains the same architecture and updates the drafter's trainable weights. Neither variant inserts experts, routing, or a new inference branch. This makes the released checkpoint itself the object of adaptation, with the original serving implementation retained.

EDA is a close and substantial predecessor: it addresses changing targets, reuses pretrained drafter components, uses target-generated responses, and limits the parameters updated during adaptation. Those ideas cannot carry ReFit's novelty claim by themselves. EDA's distinguishing mechanism is a shared/private expert decomposition inside the drafter's FFN; ReFit asks how much repair is possible **without introducing that decomposition**, using the components already present in production drafters. [EDA paper](https://arxiv.org/html/2603.09527v1#S4); [ReFit parameter selection](../followspec/family_repair.py).

The paper can make a strong positive case around three contributions together: a checkpoint-level compatibility study, controlled experiments on repair location within released drafters, and an architecture-preserving repair recipe demonstrated in autoregressive and block-diffusion drafting. The engineering difficulty of porting EDA explains why it is not an interchangeable baseline in our current engine; it does **not** establish that ReFit is more accurate, faster, or cheaper than EDA.

**Correction to the earlier feasibility memo:** EDA does not inherently require training its entire base architecture from scratch. Its paper allows initialization from a pretrained drafter, and its released loader explicitly maps a compatible conventional MLP into the shared expert. The actual prerequisite is a compatible initialization or a validated conversion. Our released EAGLE-3 weights are not directly compatible with its last-layer feature-prediction path. The earlier 1–3+ day estimate remains a rough integration estimate, not an experimentally established minimum or a scientific disadvantage of EDA.

## 2. What EDA proposes, and what overlaps

EDA combines three elements: a shared/private gated FFN, adaptation on target-generated domain responses, and hidden-state-based sample selection. The shared component retains previously learned behavior; adaptation concentrates on target-specific capacity. Its selection procedure applies PCA and scores answer states against a general-data reference using Mahalanobis distance, retaining high-scoring sequences. The experiments cover math, code and medicine in the Qwen2.5 family, with greedy and sampled decoding. [EDA §§4–5](https://arxiv.org/html/2603.09527v1#S4).

The following are **shared premises**, not differentiators for ReFit:

- A drafter can lose alignment when the target changes.
- Reusing learned drafter weights can be preferable to starting over.
- Responses generated by the new target supply useful adaptation data.
- Only part of a drafter may need updating.
- The target's original fine-tuning corpus need not be available.
- Speculative verification preserves the target's output distribution when the decoding algorithm is implemented correctly.

In particular, “training-set-free” is a property of our deployment recipe, not a unique contrast against EDA. EDA explicitly motivates regeneration when original domain training data are inaccessible. Likewise, changing the target without retraining the target itself is not exclusive to ReFit.

## 3. The algorithms adapt different parts of the computation

Let a released target-conditioned drafter be represented schematically as

\[
q_{W,\phi}(\cdot\mid x,T)
 = D_\phi\bigl(W H_T(x),\, e(x);\,\text{cache}\bigr),
\]

where \(H_T\) collects the target features, \(W\) is the existing fusion projection, and \(\phi\) contains the remaining drafter computation. This is explanatory notation, not a replacement for either architecture's actual forward pass.

For our EAGLE-3 interface variant,

\[
\widehat W
 = \arg\min_W\mathcal L_{\mathrm{native}}
       (W,\phi_0;\mathcal D_T,T),
\qquad \phi=\phi_0.
\]

The released decoder and output head stay fixed. Full repair instead optimizes the drafter's native trainable components, with verifier-owned/frozen components handled as in the training implementation. The objective is inherited from the drafter, not a newly proposed loss. In our EAGLE-3 path it is the native token-distribution objective with training-time unrolling; DFlash uses its native block objective. [Parameter scope and native loss calls](../followspec/family_repair.py).

EDA's paper instead replaces the FFN transformation by a learned combination of shared and private nonlinear experts,

\[
F_{\mathrm{EDA}}(h)=g_s(h)E_s(h)+g_p(h)E_p(h),
\]

and adapts the private component and routing while retaining the shared expert. [EDA §4.1](https://arxiv.org/html/2603.09527v1#S4.SS1).

The distinction is therefore **adapting an existing input projection versus adding target-specific nonlinear decoder capacity**. These are not two names for the same parameter subset. A generic input-dependent mixture of nonlinear experts cannot be reduced exactly to changing a single fixed linear input projection. Special parameter settings may coincide, but there is no general checkpoint-renaming conversion that makes them equivalent.

This does not imply that the private expert is unnecessary for all targets. It establishes what ReFit demonstrates: useful repair can be obtained within the already deployed architecture. An EDA-style expert augmentation of EAGLE-3 or DFlash remains a meaningful alternative to test.

| Aspect | EDA | ReFit | Significance |
|---|---|---|---|
| Adaptation structure | Shared/private FFN experts and routing | Existing feature projection, or existing full drafter | Different parameterization and export contract |
| Reused initialization | Pretrained shared components; compatible conventional drafter can initialize them | Released family drafter checkpoint directly | ReFit preserves the original model structure |
| Interface-only behavior | Not the proposed expert-adaptation mechanism; release can also train `fc` | Explicitly freezes every component except `fc` | The strict freezing constraint is a testable distinction |
| Training responses | Target-generated domain responses | Target-generated public-instruction responses; generic and self-elicited conditions | Substantial overlap; prompt source is secondary |
| Selection | Representation-based subset selection | Main recipe does not require such selection | Simpler recipe, not evidence of superior data efficiency |
| Serving artifact | Shared/private expert computation | Original model keys and supported forward graph | Existing EAGLE-3/DFlash serving support remains usable |
| Our evaluated objects | Not reproduced | Official and production EAGLE-3, plus DFlash | No empirical ReFit-versus-EDA ranking is available |
| Broader study | Domain adaptation study | Census, fixed-text controls, capacity controls, repair and serving economics | Added empirical scope, not ownership of adaptation itself |

## 4. Why transferring the released EDA implementation is substantial work

### 4.1 Its feature contract differs from our EAGLE-3 checkpoints

The released EDA data path saves the target's **last-layer hidden state**. Training shifts that sequence to predict the next hidden state. Its drafter concatenates an embedded token and a hidden vector through an `fc` with input width \(2d\). The loss combines hidden-state regression with token-distribution supervision through a frozen target head. This is an older EAGLE-style feature-prediction contract. [Feature extraction](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/data/ge_data.py#L198-L210); [model](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/model/cnets_eda.py#L674-L722); [training](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/train/main_deepspeed_eda.py#L140-L178).

Our EAGLE-3 loader instead constructs a bias-free `fc` from three target taps, of width \(3d\), and uses the released draft head/vocabulary mapping and native unrolled token objective. For the Llama path with \(d=4096\), the existing interface has shape \(4096\times12288\), hence 50,331,648 parameters. An EDA-style \(2d\) input would have width 8192 even before accounting for the different meaning of its features. The Qwen2.5 example configuration in EDA also has different hidden/vocabulary sizes. [Local native EAGLE-3 core](../.venv-followspec/lib/python3.11/site-packages/speculators/models/eagle3/core.py); [EDA example config](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/train/qwen2_7B_config.json).

Consequently, copying weights, changing a model path, and selecting private parameters would not reproduce EDA on our existing checkpoints. We must either retain EDA's original architecture and obtain a matching base drafter, or port its expert mechanism into EAGLE-3 and explicitly label that as an adaptation of EDA. The latter is scientifically useful but requires choices about initialization, capacity, routing, loss, and serving.

### 4.2 A pretrained initialization is possible, but not automatically compatible

`load_shared_experts` accepts an EDA checkpoint or maps a conventional `layers.*.mlp.*` into `shared_experts.0`. It also attempts to reuse attention, normalization, `fc`, and embeddings. This is evidence that “EDA must pretrain from scratch” would be incorrect. It is not evidence that arbitrary EAGLE-3 tensors fit: shape and feature semantics still have to match, and some assignments are not shape-filtered before loading. [Exact loader](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/model/cnets_eda.py#L724-L779).

The supplied workflow points to a local stage-1 checkpoint. We found no linked compatible Llama-3.1/EAGLE-3 or Qwen3/EAGLE-3 initializer in the inspected release. The Hugging Face paper-tag query returned an empty list; this is a limited discovery result, not proof that weights do not exist elsewhere. If compatible weights become available, a major scheduling dependency disappears.

### 4.3 A faithful data comparison requires conversion, not regeneration alone

Our saved target responses can be reused, but EDA's trainer consumes per-sample hidden-state files rather than our online multi-tap capture. Token offsets, last-layer normalization, response masks, chat templates, and the head used for supervision must agree. The EDA extractor explicitly asks users to change separators for other families. Blindly reusing its Qwen separators for Llama would invalidate the training masks. [Extractor and template instructions](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/data/ge_data.py).

EDA's selection component also needs a general-data reference and selection settings. In the inspected repository tree we did not locate a separate implementation of the paper's PCA/Mahalanobis selection step. A full-method reproduction would need to locate or implement and validate it. Omitting selection can define an architecture-only baseline, but it should not be presented as the entire EDA recipe. [Pinned tree](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/tree/a29f0381479a92d0f3114fd264cd790bab3a208b).

### 4.4 Its inference path is custom and not our frozen serving path

EDA's evaluator instantiates its own drafter, target KV-cache implementation, and tree-generation machinery. Our acceptance/timing protocol uses the frozen vLLM 0.31.0 harness with EAGLE-3 chain drafting at K=4. The new expert tensors and computation do not fit that existing EAGLE-3 loader unchanged. A faithful comparison requires either adding a supported expert model implementation or moving all compared methods into a common alternative runtime. Either route requires matched controls and verification, not just running EDA's supplied timing script. [EDA serving wrapper](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/model/ea_model_eda.py); [evaluator](https://github.com/Lyn-Lucy/Efficient-Draft-Adaptation/blob/a29f0381479a92d0f3114fd264cd790bab3a208b/eda/evaluation/gen_ea_answer_qwen2_eda.py).

The inspected wrapper imports Llama and Mixtral KV modules that are absent from the pinned repository tree. It explicitly dispatches Llama and Qwen2 architectures, with a Mixtral fallback; Qwen3 is not an explicit branch. These are concrete release-integration issues. We verified the import/path mismatch statically, not by claiming to have run a failed full EDA benchmark. Fixing packaging is likely much easier than reconciling the feature contract, initialization, and comparative evaluator.

### 4.5 What this means for the paper

The defensible deployment statement is: **ReFit preserves the released drafter architecture and its existing serving implementation; EDA's expert decomposition requires support for a different drafter computation.** The missing files, local paths and unavailable initialization explain this sprint's reproduction burden. They should generally stay in the experimental-comparison notes, not become the main scientific argument against EDA.

## 5. Paper versus code: details a reproduction must resolve

The paper and code should not be silently treated as identical specifications. These observations are scoped to the pinned release, not allegations about the authors' experiment provenance.

| Item | Observed distinction | Consequence |
|---|---|---|
| Which projection trains? | Stage-2 script passes `--freeze_attention`, not `--freeze_fc`; the trainer freezes `fc` only when that second flag is set | Do not say EDA freezes its interface; its supplied recipe adapts `fc` alongside private capacity |
| Routing | The paper describes joint shared/private softmax mixing. Code normalizes shared and private groups separately; training defaults use one expert in each group | With those defaults, each routing weight is 1 and the outputs add; this is not the paper's input-dependent two-way mixture |
| Shared router | Paper discusses adapting routing parameters; release freezes the shared router with shared experts | Choose and report which specification is reproduced |
| Checkpoint bootstrap | README describes stage 1 then stage 2; code additionally supports conventional-MLP initialization | Two-stage documentation does not prove fresh base training is mandatory |
| Feature objective | Code uses next-hidden-state regression plus token soft-target loss; ReFit's EAGLE-3 path uses native token training-time unrolling | Matching only examples/epochs is insufficient to isolate the adaptation location |
| Acceptance statistic | Paper defines accepted draft length; evaluator calculates generated tokens divided by a returned iteration counter | Audit the bonus token and counter semantics before comparing published τ with ours |

**CPU check:** extracting only the two reviewed expert classes and running a tiny CPU forward with the supplied one-shared/one-private configuration gave exactly the sum of the two expert outputs. Changing router weights did not change the output (maximum absolute differences both 0). This validates the algebraic observation for that configuration; it says nothing about EDA's published quality. Source hashes, scope and checks are saved in [audit evidence](../artifacts/REV5_EDA_deep_audit_20261012/static_and_cpu_checks.json).

Even this additive implementation is not generally representable by a change to the original fixed-size linear interface. Two nonlinear MLPs could sometimes be represented using an expanded FFN, but that still changes the original computation/parameter layout. We should not claim that all EDA variants necessarily pay a measurable routing slowdown: we have not measured that.

## 6. How much novelty does EDA leave us?

### ReFit-full: substantial conceptual overlap

If the contribution is described only as “fine-tune the old drafter on the new target's generated responses,” EDA is a strong novelty objection. Full repair is a straightforward architecture-preserving adaptation baseline; its value is its demonstrated effectiveness, cost, portability across released drafters, and the evidence explaining when to use it. It is not a new generic distillation algorithm.

EDA's main baseline comparison also does not directly measure the ReFit recipe. Its stated setup uses original adaptation data for Full-FT and LoRA, while its complete EDA variant changes the response source and selects a subset. Therefore the full-method result combines architectural and data changes. A proper ReFit-versus-EDA comparison would give both the same target-generated data first, then separately assess selection. This is a design observation, not a claim that EDA's reported results are invalid. [EDA §5.1](https://arxiv.org/html/2603.09527v1#S5.SS1).

### ReFit-interface: a concrete restricted repair choice

The interface variant is more sharply differentiated: it leaves the released decoder/head unchanged and spends adaptation capacity entirely in the existing fusion projection. This has a clear storage/update advantage and requires no additional inference operators. However, EDA already establishes the usefulness of partial drafter adaptation. Our novelty must specify **which existing component, under which released architectures and deployment constraints**, rather than claim parameter-efficient drafter adaptation itself.

Our capacity controls also delimit the interpretation. In the three-seed R1 SPEED-128 study, dense interface minus matched decoder q/o adaptation gives Δτ **−0.001 [−0.025, 0.023]**, n=128, three seeds. Thus the evidence supports an effective interface repair option, not a universal advantage over decoder adaptation. Whole-drafter LoRA is also competitive. [E8/E17 evidence](REV2-results-20261010.md).

### The empirical contribution is stronger than the recipe alone

ReFit's study connects compatibility across public checkpoints to measured repair and serving outcomes. Its controlled component comparisons, target/text supervision controls, two released EAGLE-3 initializations, and DFlash experiments are more informative than presenting warm-start training as a standalone algorithmic invention.

The parent-supervision experiment is especially useful: on identical derivative-generated sequences, derivative supervision adds **0.314 [0.288, 0.340] τ on SPEED-128** and **0.397 [0.383, 0.411] on MATH-500** for full repair (n=128/500, one seed). This establishes an incremental benefit beyond changing the text alone. It changes features and target policy together, so it does not uniquely attribute the benefit to the interface. [Y7 results](REV4-results-20261011.md).

The architecture-preserving extension to DFlash broadens the demonstrated applicability beyond autoregressive feature prediction. Use the successful Llama-family evidence specifically; the Qwen3 DFlash condition includes regressions and does not support an unqualified all-target claim. This is internal guidance on which generality statement is supported, not a request to turn the main narrative into a list of failures.

## 7. A fair direct comparison, if pursued later

Two experiments answer different questions and should be labeled separately:

1. **Released EDA reproduction:** run its compatible base/domain setting and establish that the implementation reproduces its intended behavior. This validates EDA, but it is not a head-to-head result on R1/Nemotron.
2. **Matched EDA-style adaptation on our targets:** initialize from a common compatible family drafter, add the shared/private mechanism with documented initialization, and compare against interface/full repair using the same derivative responses, masks, token budget, target, prompts and decoding conditions. Clearly label changes from the published implementation.

For mechanism isolation, first hold response data fixed and omit selection for every arm; then add EDA's selection as an explicitly separate factor. Report both matched-token and measured-compute comparisons, trainable and total parameters, and incremental inference cost. Base pretraining is a common prerequisite for both approaches and must be separated from per-target adaptation rather than charged only to EDA.

Do not compare EDA's published GPU time directly with our approximately 11 A40 GPU-hours. EDA's overhead table follows a four-H200 setup and reports training time, whereas our end-to-end measure includes generation. Nor should its τ or speedup be inserted beside ours without matching targets, proposal structure, counters, workloads and hardware. [EDA §§5.3–5.4](https://arxiv.org/html/2603.09527v1#S5.SS3).

A compatible checkpoint could shorten the prior **1–3+ day** engineering estimate considerably. Conversely, complete frozen-engine integration could take longer. There is no measured runtime supporting a stronger claim. We have not launched this work.

## 8. Proposed paper text

These are candidate passages for the owner/Claude to integrate; they are not edits to `paper/claude_final`.

### Related work: compact paragraph

> Efficient Draft Adaptation (EDA; Lin et al., 2026) addresses drafter transfer through a shared/private expert decomposition and adaptation on regenerated, selected responses. ReFit studies repair under a different constraint: preserving the architecture of an already released target-conditioned drafter. ReFit-interface updates only its existing feature-fusion projection, and ReFit-full updates the original drafter without introducing experts or routing. Both retain the released serving path. Our study complements efficient adaptation with a census of public checkpoints, controlled comparisons of repair locations, and evaluation across autoregressive and block-diffusion drafters.

Citation: [EDA](https://arxiv.org/abs/2603.09527), existing BibTeX key `lin2026eda`.

### Introduction: positive statement of scope

> We study whether the drafters already available for a model family can be repaired in place when deployed with post-trained targets. ReFit retains the released drafter architecture and its native training objective. Updating only the existing feature-fusion projection provides a compact repair option that leaves the decoder and output head unchanged; full warm-start adaptation provides a higher-capacity alternative. This formulation turns compatibility repair into a checkpoint update that uses the existing serving implementation.

### Method: what the interface variant contributes

> ReFit-interface allocates all adaptation capacity to the projection that fuses the target's hidden states. Unlike expert-based adaptation, it introduces no target-specific branch inside the drafter decoder. The resulting model has the same dimensions, operators and checkpoint structure as the released drafter, with only the interface weights changed.

### Experimental-comparison note, if needed

> EDA's released implementation uses last-layer feature prediction and a shared/private FFN, whereas our released EAGLE-3 checkpoints use multi-layer feature fusion and token-level training-time unrolling. A direct comparison therefore requires a compatible initialization and a matched implementation rather than loading the EDA checkpoint into the existing EAGLE-3 path. We evaluate architecture-compatible full and low-rank adaptation controls under matched data and training budgets; these are not reproductions of EDA.

The last passage explains scope without arguing that engineering inconvenience establishes scientific superiority. The stronger narrative is the successful in-place repair itself.

## 9. Claims to use, and claims to avoid

| Supported statement | Unsupported replacement |
|---|---|
| ReFit preserves the architecture of the released drafter | ReFit invented drafter adaptation after target changes |
| ReFit-interface changes only the existing `fc` | EDA never changes an interface |
| EDA adds expert structure; its code supports compatible pretrained initialization | EDA always requires training a new drafter from scratch |
| ReFit uses the original target-conditioned serving implementation | EDA cannot be deployed or cannot work with Llama |
| Interface repair is effective and compact | Capacity-matched results prove the interface is the unique source of damage |
| Native checkpoint compatibility avoids implementing a new expert forward path | ReFit is empirically faster or cheaper than EDA |
| DFlash repair works in the demonstrated Llama settings | Repair improves every architecture/family condition |
| We did not locate compatible public weights in the audited sources | No compatible EDA weights exist anywhere |
| Native self-distillation is shared prior practice | Generating target responses distinguishes ReFit from EDA |
